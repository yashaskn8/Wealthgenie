# WealthGenie financial architecture v2 — migration and safety contract

## Authoritative data boundaries

* **MongoDB remains authoritative for account/profile, immutable recommendations and allocation revisions, user-declared tax contexts, purchase lots, shortlist history, and private financial-calculation snapshots.** Existing MongoDB transactions are not split across databases.
* **PostgreSQL is the opt-in authority for the proposed independent financial universe**, including canonical archetypes versus actual product identities, parent categories, source rights, effective-dated rates and retained observations. Existing Mongo market-provider paths remain legacy while they are deliberately migrated one at a time; do not operate two writers for the same product/source.
* **One existing tax engine** (`services/taxEngine.js`) owns supported FY rules; the cash-flow and Monte Carlo extensions call it. No frontend tax law duplication.
* **No data-source license is granted by this repository.** The checked-in matrix at baseline reports zero rights-qualified production provider paths. No production provider rights have been enabled automatically.

## Repository implementation

New surfaces (only exposed with correct authorization/data):
* `GET /api/financial-universe` — independently paginated source-independent catalog, only when PG is configured; note that catalog identity does not indicate a price.
* `GET /api/financial-universe/:productId/observation?kind=PRICE` — blocks unlicensed, stale, revoked or expired observations.
* `GET|POST /api/investor-tax-context` — append-only, user-owned explicit investor tax context with profile version.
* `GET /api/recommendation-shortlist` / `POST /api/recommendation-shortlist/save` — up to five **already approved parent categories** per risk bucket, fewer if not eligible, no fabricated actual product eligibility.
* `POST /api/tax-aware-simulation/equity-lump-sum` — bounded user-declared *hypothetical* one-product lump-sum equity model. It is NOT live calibrated, has no multi-asset tax netting, and does not project future tax law. Net distributions are calculated from gross simulated terminal paths and the existing statutory tax engine.
* `GET|POST /api/investor-holdings` / `POST /api/investor-holdings/valuation` — explicit self-declared purchase lots and immutable mark-to-market snapshots using rights-qualified INR product observations; no realized gain or tax is inferred.
* `calculateQualifiedProductCashflow({taxEventContext})` — optional tax-event extension only for source-qualified annual payout contracts when explicit cash-flow settlement dates and every affected fiscal-year tax context exist.

No new actual scheme/fund/stock identity is generated from marketing text. The four new private investor APIs require `FINANCIAL_ARCHITECTURE_ENABLED=true`; the public SQL investment directory independently requires `FINANCIAL_POSTGRES_ENABLED=true`. Both default off. Existing core recommendation flows remain independently available.

## PostgreSQL activation checklist (not completed automatically)

1. Obtain a managed PostgreSQL instance and set `FINANCIAL_POSTGRES_URL` via deployment secret management, with `sslmode=verify-full` in production; use certificate verification, least-privilege roles, backups, restore drills and monitoring.
2. **Runtime dependency resolved:** `pg@8.16.3` and its dependency graph are now pinned in `server/package.json` and `server/package-lock.json`. The lockfile was generated by npm in a one-time branch-only GitHub Action, then the temporary workflow was removed. `npm ci` must still pass on the exact release commit. The managed PostgreSQL instance and connection secret remain external deployment requirements.
3. With the driver installed, run `npm run finance:pg:migrate` and `npm run finance:pg:seed` from `server/` on the intended database. The seed stages **155 legacy + 95 documented discovery archetypes = 250 entries** in PostgreSQL, all as `ARCHETYPE`, `UNVERIFIED`, and `recommendation_eligible=false` in this independent discovery store. The 95 additions do not represent verified purchasable securities. The original 155 legacy recommendations retain their existing, separately controlled MongoDB authority.
4. Review every actual product identity against an authoritative identifier and create `ACTUAL_PRODUCT` rows with explicit source identifiers and product terms. Ingest only authenticated provider responses from a verified rights register, never from a user-submitted price or URL.
5. Record source-specific permissions, including extraction, storage, derivation, public display, commercial use and any redistribution requirement, **with documentary evidence and approved retention time**. Rights default false. Upstox/AMFI/RBI/India Post data do not become unrestricted merely by being copied into SQL.
6. Run `MONGODB_MIGRATION_URI=... npm run finance:mongo:migrate-indexes` against the correct Mongo replica set. This explicitly provisions the unique/private identity indexes and `retainedUntil` TTL required for derived valuation snapshots. The new private routes fail closed until startup verifies those indexes.
7. Only after the database migrations and permission qualifications, set `FINANCIAL_POSTGRES_ENABLED=true` and `FINANCIAL_ARCHITECTURE_ENABLED=true`. Enabled startup fails if the PostgreSQL authority or Mongo private indexes are absent. Verify quote freshness, product/provider exact identities, correction revisions, time zones, source-rights revocation, secure connection and read-time permissions.
8. Schedule `npm run finance:pg:prune` and `MONGODB_MIGRATION_URI=... npm run finance:mongo:prune-valuations` under deployment orchestration, and run both promptly after a provider right is revoked or expires. The first purges expired/revoked SQL observations and terms; the second performs required erasure of derived private snapshots for revoked sources in MongoDB. Read-time rights checks reject disallowed observations before cleanup, but physical erasure requires the operational jobs to execute.
9. Reconcile all existing licensed market observations with the new PostgreSQL representation, use a provider-by-provider cutover behind feature flags, and keep exactly one authoritative writer per provider/product. Do not dual-write MongoDB and PostgreSQL inside separate uncoordinated transactions.

## Financial-safety rules

* Explicit zero and unknown/null are different; annual gross income must never be inferred from net take-home pay.
* No post-tax number exists without matching dated tax rules, product tax classification, the user's financial context, and the applicable source facts.
* Gross contractual cash flow, realized gain, current market price, unrealized holding valuation, historical return, and simulation are distinct metrics. A saved purchase lot is not a verified **current quantity** without the user's complete sale/transfer/corporate-action history; lot valuations are explicitly illustrative until reconciled.
* A live-price observation is not a post-tax return. A bank published rate is not a live traded quote.
* The equity model is a **single user-declared hypothetical**. It cannot claim all 250 discovery archetypes, 15 eligible actual products, future legislation, brokerage fees, loss set-offs or security-level suitability.
* Source expiry must invalidate both reading and retaining derivative snapshots; MongoDB valuation snapshots have a TTL bound to market observation and provider-rights expiration. Run the cross-database rights-revocation janitor promptly; MongoDB TTL alone is not instantaneous and cannot detect early source revocation.
* Never persist post-tax results inside immutable Recommendation documents. All new results are independent append-only snapshots.
* No cross-user records may be loaded or calculated; all investor routes enforce JWT and user-scoped profile ownership.

## Additional deep red-team and deployment controls

**SEBI advisory-compliance gate:** India's investment-adviser regime can apply to personalized investment/portfolio advice depending on the service's facts, compensation and regulatory exceptions. Before consumer production launch, obtain documented legal/compliance sign-off, including any required SEBI registration, client agreement/terms, suitability records, conflicts disclosures, grievance process and cybersecurity/privacy obligations. Regulatory registration is **not** established by this repository or by passing financial unit tests. Official sources: https://www.sebi.gov.in/legal/regulations/nov-2025/securities-and-exchange-board-of-india-investment-advisers-regulations-2013-and-securities-last-amended-on-november-25-2025-_98246.html and https://www.sebi.gov.in/legal/master-circulars/feb-2026/master-circular-for-investment-advisers_99569.html.

**Provider commercial-use gate:** AMFI's published website terms restrict third-party commercial reproduction, derivative work and significant electronic storage without written authorization (https://www.amfiindia.com/terms-of-use). NSE's published usage policy requires licensed subscriber arrangements for commercial market data (https://www.nseindia.com/static/market-data/nse-data-policy). This project's CI fake rights grants concern **isolated synthetic fixtures only**; no production provider license is approved.

**Tax-engine coverage gate:** The validated cash-flow engine extension supports *source-qualified scheduled ordinary-interest events* only. The Monte Carlo extension supports *a single hypothetical equity lump sum* only. No broad claim can be made that all 250 archetypes support after-tax projected outcomes, SIP tax lots, multi-product offsets, losses, actual withholding timing, future statutory rules, or verified individual security recommendations.

**True current-holding gate:** Purchase lots do not establish live positions without sales, transfers and corporate-action reconciliation. The API deliberately labels such valuations illustrative and unreconciled. A holdings transaction ledger plus qualified position reconciliation is required before advertising live current portfolio values.

**Backend-gated rollout:** CI must be green on the exact merge commit, including the isolated PostgreSQL rights/identity/purge integration, financial MongoDB TTL/unique migration, frontend E2E navigation, and adverse input tests. Verify real disaster recovery, rollback, exact identity, and removal of revoked derived data. New frontend extension flags must be set only after backend migrations and rights approval.

## Release blockers still requiring independent evidence

* The `pg` lockfile is committed, and isolated PostgreSQL migrations/rights integration tests pass in CI; a production PostgreSQL instance, production roles/secrets, backups and restores, and live provider integration remain unverified.
* Provider rights for production live data are currently unqualified; no URL, key or waiver may be fabricated.
* Existing provider-specific MongoDB market-data ingestion has not been cut over to PG; a rights-approved ingestion adapter with exact provider product identities, live source authentication, corrections and rollback has not been deployed.
* **Licensing release gate:** AMFI's published terms restrict significant storage, derivative works and public/commercial use without separate authorization. NSE commercial market-data usage generally requires a subscriber agreement. Do not enable their rights or preload scraped NAV/quotes merely to satisfy coverage.
* The 95 new entries remain discovery-only. The complete directory and Top-5 bucket UI also require their respective `VITE_FINANCIAL_POSTGRES_ENABLED=true` and `VITE_FINANCIAL_ARCHITECTURE_ENABLED=true` frontend flags on a deployment with matching backend gates. Otherwise the UI makes no finance-extension requests. Up to 5 per risk group is implemented with existing authoritative parent-category suitability; individual securities are not promoted without verified product facts.
* The new private financial MongoDB indexes require an explicit migration and a successful read-only startup gate before the private feature flag can be enabled.
* All 250 canonical archetypes pass identity uniqueness and PostgreSQL reconciliation. However the 95 new entries are **discovery archetypes only**; none has individual verified issuer/scheme IDs, product-specific eligibility, licensed current prices or post-tax outputs. Calling these 250 purchasable products would be inaccurate.
* Full multi-asset, multi-year path-specific tax simulation including capital losses, contributions, withdrawals, fees, and future-tax uncertainty is not implemented. Only the explicitly bounded scenario described above is available.
* Product-level suitability beyond authoritative parent-category screening is unverified.
* CI, real database integration, concurrency, migration rollback, active runtime rights and load results must be checked before release.

**Do not mark this branch production-ready solely because a source commit or CI unit-test job passes.**
